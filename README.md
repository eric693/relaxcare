# RelaxCare 按摩／SPA 連鎖營運管理系統

給按摩、SPA、整復連鎖店用的營運系統。處理的是別的行業沒有的三件事：
**輪鐘制的公平性**、**抽成分潤的正確性**、**預收款的負債管理**。

錢會被人碰到的地方，一律「系統算一套、人記一套，差額留下來」——
日結的短溢、盤點的差異、班表與簽到的落差都是這個原則的產物。

## 三個核心引擎

### 1. 輪鐘（`src/rotation.js`）
輪序 =（已輪次數 `rounds`，簽到順序 `queue_seq`）由小到大。先比輪次再比簽到，
所以「輪過的人自動排到隊尾」不必真的搬動號碼，補簽到的人插進來也不會亂。

- **指名預設不吃輪**（`rotation_designate_counts=0`）：否則紅牌會被指名指到接不到輪鐘，等於變相減薪。
- **休息是暫離輪序不是下班**，設定的時間到了自動回到輪序（現場沒有人會記得按恢復）。
- 每一次簽到、指派、被跳過、人工調整都寫進 `queue_logs`；人工調整**必須填原因**。
  這張表存在的唯一理由是「技師吵架時拿得出來」。

### 2. 抽成分潤（`src/commission.js`、`src/payroll.js`）
**抽成在結帳當下算好、寫死在單據上**（`tickets.comm_*`），不是月底回頭套現在的％——
比例調過一次，過去的薪資就全部對不起來，而技師記得自己上個月領多少。

％優先序：服務項目自訂 → 技師自訂 → 級別預設（`settings.level_rates`）。
抽成一律進位到**整數元**：算到小數會讓薪資頁與損益頁永遠差幾毛，那是解釋不完的。

薪水 = 底薪＋服務抽成＋商品抽成＋指名費＋預收銷售抽成＋業績級距獎金＋加項－扣項。
級距獎金只看服務業績，不含商品與預收——否則會鼓勵只賣卡不做鐘。

### 3. 預收負債（`src/prepaid.js`）
儲值與次卡是**負債不是收入**。

- 現金部位與贈送部位**分開存**。退款只退未使用現金，贈送金一律作廢
  （「儲值 2 萬送 3 千、用掉 5 千後退款」混在一起算就會退錯錢）。
- 扣款一律**先扣贈送金**（會過期的先用掉）。
- 次卡單次價值 = **實付 ÷ 總次數**，不是原價（用原價攤會讓卡在用完前就把負債沖光）。
- 退卡兩種算法都試算：按實付單價退未使用次數／已使用次數按原價扣回。
- 餘額欄位是快取，`wallet_txns` / `pass_txns` 流水才是真相。

### 4. 現金與庫存的落差（`src/closing.js`、`src/inventory.js`）
櫃檯的抽屜與架上的商品是系統唯一管不到的地方 —— 那裡的真相在人手上。
所以這兩個模組都長成同一個形狀：**系統算出「應該是多少」，人輸入「實際是多少」，差額必須留下來。**

- 日結：應有現金 = 零用金 ＋ 鐘單收現 ＋ 儲值收現 ＋ 售卡收現 － 現金支出 － 現金退款。
  點鈔照面額填張數，短溢超過容忍值（預設 50 元）**一定要寫原因才存得起來**。
  鐘單以「結帳時間」歸班，不是營業日 —— 早班的客人做到晚班才結帳，那筆錢在晚班的抽屜裡。
- 庫存：`stock_txns` 是真相，`retail_products.stock` 只是加總快取（跟儲值金同一套規矩）。
  進貨、退貨、銷售出庫、盤點、跨店調撥各是一筆流水；成本用**移動加權平均**，
  出庫時記下當下的成本，商品毛利才算得出來，而且日後進價再變也不會回頭改到已經賣掉的那幾件。

## 上鐘閘門（`src/gates.js`）

開單／改單／上鐘前一次跑完：技師時間重疊、床位佔用（足療區可設同時多組）、
**客人健康禁忌 vs 服務項目**、技師可做項目、房型相符、技術士證與健檢到期、
每日時數與連續上鐘、付款可行性（儲值餘額、次卡效期與歸屬）。

`conflict` 是硬衝突，可強制放行但**必須填理由**，理由寫進 `tickets.gate_note` 與稽核軌跡。
`warn` 只是提醒。餘額不足是 warn 不是 conflict——結帳試算本來就會「儲值抵到底、不足收現金」，
擋下來會與同一畫面上的試算自相矛盾。

## 法遵：民俗調理業（`src/compliance.js`）

按摩、推拿、腳底按摩屬民俗調理業，不得從事醫療行為或宣稱療效。實務上被檢舉的多半是**文案**。
系統掃描服務項目、商品與對外設定文字，找出「治療／療效／根治／整脊」等字詞並指出位置，
**不自動改文案**（改壞了更糟）。另有技術士證與健檢到期總表、客人同意書與問診完整度。

## 發票、集點與同意書

**發票（`src/invoicing.js`）**：系統不代開電子發票，它記的是「實際開了哪幾張」。
作廢＝整張不算數；折讓＝原發票有效、銷售額扣掉折讓金額 —— 這兩個實務上最常搞混。
沒有這張表，營業稅試算永遠對不回申報書。

**集點與介紹（`src/loyalty.js`）**：兌換一律換成**儲值贈送金**，不直接折在鐘單上。
折鐘單會壓低 `net_amount`，而抽成是按業績算的 —— 客人用點數、技師薪水就變少，那是吵不完的。
走贈送金則沿用既有的預收流程，負債、退款、優先扣抵全部已經是對的。

**電子同意書（`src/consent.js`）**：`compliance.js` 早就會算「同意書完整度」，
但系統裡原本沒有地方可以**簽**。同意書是快照不是外鍵：客人當下自述的健康狀況、
簽的是哪一版條文，日後改資料都不影響已經簽的那一份。

## 檔案上傳：存檔不能只是「沒噴錯」（`src/storage.js`）

客人照片、進貨單據、同意書簽名都走同一條路，每一次存檔跑完四步：
**寫入暫存檔 → fsync 落盤 → 改名到正式位置 → 回讀整個檔案重算 SHA-256 與位元組數比對。**
任何一步對不上就刪掉半成品、丟出錯誤，畫面照實顯示失敗。

`fs.writeFileSync` 沒有丟例外，不代表資料真的落到磁碟：可能只到作業系統快取、
可能磁碟滿了寫進去半截、可能前端傳來的 base64 本身就被截斷。這幾種情況的共同點是
——「畫面顯示上傳成功、檔案其實是壞的」，而它要等到幾個月後有人來調同意書時才會爆。

指紋存進資料庫，每日維護會整批重驗一次，讀取檔案時也會再驗一次（壞檔回 410 而不是送出爛資料）。
「備份與檔案」頁看得到檢查結果。

## 指令

```bash
npm start                # 啟動（正式站用 pm2）
npm run seed             # 重建示範資料（兩家分店、12 位技師、60 天營運紀錄）
npm test                 # 一致性（約 2.8 萬項）＋ 上傳邊界（43 項）＋ 時區（47 項）
npm run test:concurrency # 並發：同時做同一件事會不會生出兩筆帳（需要伺服器在跑）
npm run test:timezone    # 時區：換一個 TZ 跑，結果必須一模一樣
npm run e2e              # 用真的瀏覽器走完一輪操作（需要 playwright-core）
pm2 restart relaxcare
```

四支測試各自守著不同的東西，不要互相取代：

| 指令 | 守的是 | 什麼時候一定要跑 |
|---|---|---|
| `npm test` | 同一個數字在不同模組算出來一樣；上傳的檔案真的落盤且完整；時間全都是台北 | 改財務、抽成、輪鐘、預收、庫存、上傳、任何跟時間有關的東西之後 |
| `npm run test:concurrency` | 兩個人同時做同一件事只會成立一筆 | 改日結、結帳、庫存、點數、發票的寫入路徑之後 |
| `npm run e2e` | 真的瀏覽器走得完整條流程，畫面沒有 JS 錯誤 | 改前端、或動到跨模組的流程之後 |

改動財務、抽成、輪鐘、預收邏輯後**務必重跑 `npm test`**（約 2.8 萬項）：它驗證的是
「同一個數字在不同模組算出來必須一樣」——鐘單付款拆解 ↔ 應收、儲值餘額 ↔ 流水加總、
薪資抽成 ↔ 每張鐘單抽成、損益營收 ↔ 鐘單加總、預收負債 ↔ 儲值與次卡剩餘、
輪鐘檯排序 ↔ (rounds, queue_seq)、**庫存 ↔ 庫存流水、點數 ↔ 點數流水、
日結短溢 ↔ 實點減應有、發票未稅＋稅額 ↔ 含稅總額、附件指紋 ↔ 磁碟上的檔案**。

## 時區：全站基準是台北，而且是強制的

主機的系統時區是 UTC，所以「跑在台北時間」這件事每一個進入點都要各自負責。
`src/db.js` 開頭那一行必須在 `require('better-sqlite3')` 之前 ——
SQLite 的 `datetime('now','localtime')` 是在載入的當下決定要用哪個時區的。

**不看環境變數 `TZ`，而是自己指定**：

```js
process.env.TZ = process.env.RELAXCARE_TZ || 'Asia/Taipei';
```

原本寫的是 `process.env.TZ || ...`，意思是「部署環境說了算」。但部署環境的 TZ 常常是
別人（容器映像、systemd、pm2 的父行程）順手設的，沒有人會意識到它會把整套系統的營業日
推移八小時。真的要換請明確設 `RELAXCARE_TZ`，那是有人特意打出來的決定。

三個踩過的陷阱：

1. **`toISOString()` 永遠輸出 UTC**，完全不理會 `TZ`。「備份與檔案」頁曾因此顯示
   比檔名早一天的時間（檔名 09-05，畫面 09-04 16:00）。要格式化時間請用 `fmtStamp()`／`fmtDate()`。
2. **前端的「今天」不能問瀏覽器要**。櫃檯平板時區設錯或時鐘不準，就會看到別天的輪鐘檯，
   然後來說系統壞了。`/options` 會回傳 `server_now`，`UI.syncClock()` 存下差值 ——
   存差值而不是存日期，頁面開著過午夜也還是對的。
3. **`toMinutes`／`fromMinutes` 刻意走 UTC**，那是純算術，與時區無關。
   不要「順手」改成本地時間，會在有夏令時間的地區出錯。

`npm run test:timezone` 會用 `TZ=America/New_York` 與 `TZ=UTC` 各跑一次同一支探針，
比對營業日換算與日期運算的結果是否完全相同。

## 並發：為什麼「同步」不等於安全

better-sqlite3 的每一次呼叫都是同步的，會擋住 Node 的事件迴圈直到做完。
所以在**單一行程**裡，`db.transaction(...)` 中間不可能插進另一個請求 ——
兩個櫃檯同時按下日結，第二個請求根本還沒開始跑。

很容易由此得出錯誤結論：「反正是同步的，不會有並發問題」。有兩個破口：

1. **多行程**。pm2 開 cluster、或有人在伺服器還跑著的時候執行 `npm run seed`、
   跑一支修資料的腳本、開 sqlite3 CLI 改東西 —— 那都是第二個行程。
2. **使用者的重複送出**。網路慢時櫃檯會連按兩下，或按了沒反應就重新整理再按一次。

`npm run test:concurrency` 兩種都測：前者真的 spawn 好幾個 Node 行程直接寫同一個 .db，
後者同時送出 5 個一模一樣的 HTTP 請求。驗的是「同時日結只成立一張」「庫存不會變成負數」
「同一張鐘單只結得了一次帳」「同時兌換 5 次只扣一次點」這幾件會直接變成金錢損失的事。

## 上傳：檔頭與檔尾都要驗

`storage.js` 除了回讀比對指紋，還驗**檔案有沒有完整地結束**（PNG 的 IEND、JPEG 的 FFD9、
GIF 的 0x3B、WebP 的 RIFF 長度、PDF 的 %%EOF）。

只驗檔頭會漏掉最常見的一種壞檔：**傳到一半斷線**。前幾個位元組完好無缺，檔頭檢查照樣通過，
存進去卻是一張只有上半截的照片 —— 而且縮圖可能還顯示得出上半部，
要等到有人把它放大、或列印同意書時才發現下半截是灰的。

## 損益的組成

```
毛利 = 服務營收 − 技師抽成 − 商品銷貨成本
淨利 = 毛利 − 營運費用
```

**商品銷貨成本一定要扣。** 原本沒扣，於是匯出的損益表把「商品銷貨成本」列成一行、
底下的「毛利」卻沒有減掉它 —— 各列加起來對不上總數，拿給會計看第一眼就會被抓包。
成本取自庫存流水（賣出當下記下的成本），不是月底回頭用現在的進價套算。

底薪不在這裡扣（它是固定成本，登在費用登錄），避免同一筆錢被算兩次。

## 已知的坑

1. **抽成必須是整數元**。任何地方改回 `money()`（兩位小數），一致性測試的
   「薪資抽成 = 鐘單加總」立刻會紅——兩邊四捨五入的位置不同。
2. **取消鐘單要還四樣東西**：技師輪次、儲值扣款、次卡核銷次數、商品庫存（再加上點數與發票）。
   漏一樣就會有人來吵。每日維護自動標記「未到」的那條路徑同樣要還 ——
   預約單也可能先賣了商品，漏掉就變成「客人沒來、東西也沒賣，架上卻少一件」。
3. **示範資料不能讓同一位技師時段重疊**，否則一致性測試會抓到「重疊卻沒有放行理由」。
4. `expenses` 沒有 `active` 欄位，不能用 `crud.js` 的預設清單／刪除，
   自訂的路由必須註冊在 `attach()` **之前**才會被優先命中。
5. 每日維護會把前一天還掛在檯面上的班關掉，否則今天的輪鐘檯會混進昨天的人。
6. **庫存只能走 `inventory.js`**。任何地方回頭直接 `UPDATE retail_products SET stock`，
   一致性測試的「庫存 = 流水加總」立刻會紅，而且商品成本會從此查不到出處。
7. **點數兌換不要改成直接折鐘單**。那會壓低 `net_amount`，技師的抽成跟著變少 ——
   薪資對不上的客訴會直接找上店長。
8. 業務規則的錯誤是丟例外出來的，`server.js` 的錯誤處理會把它們回成 400（帶原訊息），
   只有 TypeError 這類程式錯誤與 SqliteError 才是 500。新模組沿用這個約定就好，
   不必每支路由自己包 try/catch。
9. **`npm run seed` 會清空 `data/uploads/`**。只刪 `attachments` 資料列會留下一堆沒人認領的
   照片與簽名檔，那是客人的個資，而且每跑一次就多留一批。
   正式站上若出現孤兒檔案（例如剛還原完），用「備份與檔案」頁的「清除無主檔案」處理。
10. **床位使用率的「一天營業幾分鐘」不能用 close 減 open**。這一行有兩種常見營業型態
    會壞：24 小時店（00:00–00:00）算出 0 分鐘、營業到凌晨的店（11:00–03:00）算出負數。
    用 `finance.openMinutesOf()`。
11. **次卡的實付不能高於原價總值**。次卡是「先付錢換折扣」，賣得比原價貴幾乎一定是打錯，
    而且會讓退卡的兩種算法反轉（原價法退得比單價法多，等於送錢）。`buyPass` 會擋。
12. **日結的現金支出用「登錄時間」歸班，不是 spend_date**。用日期的話，
    同一天分早晚兩班結時，兩張日結都會扣掉當天全部的現金支出。
13. 刪除示範資料的順序要由「有外鍵的一方」往回刪：`consents`／`point_txns` 指向 `members`，
   `rosters` 指向 `therapists`，先刪 members 會直接違反外鍵（見 `scripts/seed.js` 開頭）。
